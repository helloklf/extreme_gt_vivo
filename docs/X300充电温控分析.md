# X300(V2509A)充电温控实现分析与提速突破口

> 实测设备:vivo X300(V2509A / PD2509),MTK MT6993,内核 `6.12.58-android16-6-g0a092cc0037a-abogki521987229-4k`,
> 系统指纹 PD2509,但 **vendor 指纹是 PD2502(X300 Pro)**,属于混刷状态(见 §1.3)。
> 方法:线上 sysfs/thermal/debugfs 实测 + 从 vendor_boot 提取 `vfcs-cms-core.ko` 反汇编 + DT 表解析。
> 日期:2026-11-02

---

## 0. 一句话结论

1. **"伪装主板温度时电池温度跟着变"不是传感器别名**,而是旧 `tpoff` 同时写了 `fixed_temp`;
   X300 上 `fixed_temp` 就是**电池温度**的全局替代值,而主板温度走的是另一个独立节点
   `primary_board_temp`。只写 `primary_board_temp` 时,`battery/temp` 与 `thermal_zone2` 完全不动。
2. **但只改主板温度也提不了速**:当前充电参数集是 `intell_param_type=3[chg]`,查
   `vivo,chg-primary-fbon-tc-data`,这张表在 ≤40.9 °C **恒为 2700 mA**。把主板温度伪装到 25 °C
   依然是 2700 mA,只有到 45 °C 才掉到 300 mA。**在 X300 的这个工况下,温度不是瓶颈,参数集选择才是。**
3. 于是"充电伪装在 X300 上不好使"有两个独立原因:
   - `fixed_temp` 的副作用(用户看到的现象);
   - `chg` 表是平的(真正没效果的原因)。
4. 可用的提速杠杆:
   - **原装闪充头 + `tpoff`** → 实测参数集切到 `sp`(`vchg_state=2`),板温覆盖后
     电池电流 2.47 A → 7.44 A、功率 10 W → 32 W(§6A/§6B);
   - **`tpoff`(统一版)**:安装时探测 `fixed_temp` 是否影子电池温度,自动选择
     "只写板温"(X300)或"板温+电池温同步"(iQOO15),可安全回滚;
   - **`cmsboost`(未验证)**:第三方头走 `chg` 表时可把 CC 从 2.7 A 抬到 3.5 A,
     但**没有任何实测证明能提速**;PPS/UFCS/原装头下它不接管(§6D)。
   - **已放弃/不推荐**:内核模块改表(加载即 panic)、`cms_enable=0`(保护全丢),见 §7。

### 1.2 驱动是模块,但不在 `/vendor/lib/modules`

`lsmod` 里有 `vfcs_cms_core`(1.19 MB),但 `/vendor/lib/modules`、`/vendor_dlkm/lib/modules`
都**没有** vfcs 系列 `.ko`。它们来自 **vendor_boot 的 ramdisk**:

- 解包后从 `lib/modules/` 提取到 `x300/vendor_modules/vfcs-cms-core.ko`(2,395,264 B);
- 注意:vendor_boot 里模块的 vermagic 是 `6.12.58-android16-6-g34069a564b04-4k`,
  与运行内核 `/proc/version` 的 `g0a092cc0037a` **不一致**,但模块确实已加载 ——
  这是混刷/ABL 版本串导致的现象,**做模块时以 vendor_boot 里的 .ko 为模板即可**。

### 1.3 混刷的影响

`ro.vendor.build.fingerprint` 是 PD2502(X300 Pro),系统是 PD2509。两者的 DT、NTC 布点、
充电表可能不同。本文所有 DT 数值都来自**当前运行设备**,不是文档值。

## 2. CMS 的充电电流是怎么算出来的

### 2.1 链路

```
vfcs_cms_main_work(每 2 s)
  └─ vfcs_cms_get_intell_chg_current(ctx, fb_state, vchg_state, temp_pri, temp_par, temp_bat)
       ├─ vfcs_cms_select_intell_param_type()   // 选参数集: 0=sp 1=eq 2=bypass 3=chg 4=qc 5=ai-rate
       ├─ vfcs_cms_get_current_by_temp(ctx, 表, 表头, temp, idx)   // idx 0/1/2 = primary/parallel/bat
       └─ final = primary ? primary : max_power_limit
                  min(final, parallel), min(final, bat)
       └─ vote(INTELL_CHG_EVENT, final)
  └─ vote(NORMAL_CHG_EVENT, normal_tc 查表值)     // 按 vbat 的 step 表
  └─ vote(MAX_POWER_LIMIT_EVENT, 12000)
  └─ vote(USER_IBUS, 适配器决定的输入限流)
```

votable 层再做 Min 合成,最终写充电 IC。`/sys/kernel/debug/pmic-votable/USER_IBAT/status` 可以直接看到谁在卡。

### 2.2 表的格式

`vfcs_cms_get_current_by_temp(ctx, data, rc, temp, idx)`:

- `rc[0] = 行数`,`rc[1] = 3`;
- `data` 是 `行数 × 3` 的 int32 数组,每行 `{temp_low, temp_high, current_ma}`,温度单位 0.1 °C;
- 命中条件 `temp_low <= temp <= temp_high`,**从前往后线性扫,首个命中即返回**;
- 扫不到返回 0;`行数 < 1` 也返回 0;
- `-8888 / 8888` 只是数据里的开区间端点,没有任何特判;`0xFFFFFFFE` 表示该行 lower 为负的哨兵。

### 2.3 实测日志逐行解释

```
vfcs_cms_select_intell_param_type: intell_param_type=3[chg],switch_state=0,vchg_state=[0 0],
    intell_param_enable(sp=1,eq=1,bypass=0,chg=1,qc=1,ai-rate=0)
vfcs_cms_get_current_by_temp: primary_temp,temp=355,get current_ma=2700
vfcs_cms_get_current_by_temp: parallel_temp,temp=-400,get current_ma=0
vfcs_cms_get_current_by_temp: bat_temp,temp=326,get current_ma=0
vfcs_cms_get_intell_chg_current: wired_chg fb_on,temp(pri=355,par=-400,bat=326),
    final_cur_ma=2700,primary_ma=2700,parallel_ma=0,bat_ma=0,st=3,step=7720
vfcs_cms_get_normal_chg_current: normal_tc,temp=326,ibat_ma:7720,index:4,...
vfcs_cms_main_work: ... ibus_vote(NORMAL_CHG_EVENT)=2000,ibat_vote(INTELL_CHG_EVENT)=2700
```

- 参数集 = **3 = chg**;
- primary 表在 35.5 °C 给 **2700 mA**(chg 表);
- parallel 温度无效(-40.0 °C),bat 表返回 0(X300 上 chg 的 bat/parallel 表都是 0 行);
- final = 2700;
- 另一路 NORMAL_CHG(按 vbat 的 step 表)在 4.39 V 给 **7720 mA**,不是瓶颈;
- 输入限流 2000 mA(5 V/2 A 适配器)。

## 3. 温度链路:谁是谁(核心)

### 3.1 实验:写 `fixed_temp`

| 动作 | `primary_board_temp` | `main_batt_temp` | `bat_btb_temp` | `battery/temp` | `thermal_zone2` |
|---|---|---|---|---|---|
| 基线 | 306 | 325 | 365 | 325 | 32600 |
| `echo 399 > fixed_temp` | 306 | **399** | 365 | **399** | **39900** |
| `echo 0 > fixed_temp` | 306 | 325 | 365 | 325 | 32500 |

→ `fixed_temp` 是**电池温度**的替代值,直接影响 gauge/`battery/temp`/热区,与主板温度无关。

写入单位在不同机型上并不统一:X300 上写 `399` 就得到 399(0.1°C),而有的机型写 `40` 会得到 400
(即固定值以 °C 为单位,写 0.1°C 值时要 /10)。模块的处理:

- 安装时 `customize.sh` 写入低测试值 `10`，用 `dumpsys battery` 的结果判断倍率；再用
  `main_batt_temp` 是否跟随写入后的有效值判断模式：跟随则只写主板温度(`board`)，不跟随则同时写入(`both`);
- 结果分别写进 `tpoff_mode` 和 `fixed_temp_scale`,`service.sh` 原样传给 `tpoff`;
- `tpoff` 自己不做任何探测:按 `mode` 决定只写板温还是两个都写,按 `scale` 换算 `fixed_temp`
  的写入值(板温、电池温等其它节点一律是 0.1℃,不需要换算)。

### 3.2 实验:写 `primary_board_temp`

| 动作 | 节点回读 | `main_batt_temp` | `battery/temp` | 日志 `pri=` | chg 表输出 |
|---|---|---|---|---|---|
| 基线 | 358 | 327 | 327 | 358 | 2700 |
| `echo 250` | **250** | 327 | 327 | **250** | 2700 |
| `echo 300` | 300 | 327 | 327 | 300 | 2700 |
| `echo 350` | 350 | 327 | 327 | 350 | 2700 |
| `echo 400` | 400 | 327 | 327 | 400 | 2700 |
| `echo 450` | 450 | 327 | 327 | 450 | **300** |
| `echo 0` | 355(真实值) | 327 | 327 | 355 | 2700 |

→ `primary_board_temp` 是**独立的主板温度覆盖**,不动电池温度;写 0 解除覆盖,节点回到真实值
(实测覆盖值可稳定保持 30 s 以上,不是一次性)。

### 3.3 结论

- **别名发生在 `fixed_temp` 上,不在传感器上。** 旧 `tpoff` 每轮同时写 `primary_board_temp` 和
  `fixed_temp`,于是电池温度跟着走 —— 这是工具自己造成的,不是 X300 的传感器问题。
- X300 的 `battery/primary_board_temp` 节点**不存在**,所以旧 `tpoff` 退出时读真实值失败,
  `primary_board_temp` 的还原是缺失的(靠写 0 才行)。这是旧工具的第二个 bug。

## 4. X300 的 DT 表

### 4.1 规模

`/sys/firmware/devicetree/base/soc/vfcs_cms/` 下 125 个属性,其中 tc-data 表按
`{sp,eq,bypass,chg,qc} × {primary,parallel,bat} × {fbon,fboff}` 组合,外加
`wls-*`(无线)、`car-*`、`calling-*`、`exhibition-*`、`weixin-*` 场景表。
iQOO15 只有 4 张主表,这是两代机型最大的结构差异。

### 4.2 五套参数集的关键数值(0.1 °C / mA)

**chg(当前在用,`vivo,chg-primary-fbon-tc-data`,fbon 与 fboff 相同)**

| 温度 | 电流 |
|---|---|
| ≥45.0 | 300 |
| 43.5–44.9 | 500 |
| 42.0–43.4 | 1000 |
| 41.0–41.9 | 1500 |
| ≤40.9 | **2700** |

**sp(闪充,`vivo,sp-primary-fbon-tc-data`,亮屏)**

| 温度 | 电流 |
|---|---|
| ≥45.5 | 1800 |
| 43.0–45.4 | 2800 |
| 42.0–42.9 | 3200 |
| 38.0–41.9 | 3600 |
| 37.0–37.9 | 4600 |
| 36.0–36.9 | 6200 |
| 34.0–35.9 | 7700 |
| 33.0–33.9 | 10000 |
| ≤32.9 | **15600** |

**sp 灭屏(`fboff`)** 在 35.9 °C 以下同样是 15600,但 36–37.9 °C 档是 10000(亮屏 7700)、
38–39.9 °C 档 8500(亮屏 3600)。**这就是 fbpat(fbon→fboff)在 X300 上的价值区间:36–40 °C。**

**qc**:≤39.9 °C → 3500,往上 2500/2000/1500/1000/700。
**bypass**:≤39.0 °C → 5000。
**eq**:与 sp fbon 基本相同。

电池表(`bat`):

| 表 | 行为 |
|---|---|
| `sp-bat-fbon` | 全温区 15600(等于不限) |
| `sp-bat-fboff` | ≥44.7 °C → 2900,否则 15600 |
| `chg-bat` / `qc-bat` | 恒 0(不参与限流) |
| `eq-bat-fboff` | ≥44.7 °C → 2600 |

### 4.3 chg 表为什么是平的

`chg` 是"非 vivo 协议充电器"的兜底参数集。X300 对它只给了一条 41 °C 以上才降档的保守曲线,
41 °C 以下恒定 2700 mA(≈11.6 W @4.3 V),对应 5 V/2 A 级别的适配器。
**温度伪装在这个区间内不可能有任何收益** —— 这正是"伪装不灵"的机理。

### 4.4 高 SOC 还有一层 step 表

`vivo,normal-tc-data`(按 vbat 分档):

| vbat | ibat |
|---|---|
| ≤4.18 V | 15600 |
| ≤4.24 V | 11720 |
| ≤4.29 V | 9720 |
| ≤4.48 V | 7720 |
| >4.48 V | 5505 |

实测 86% SOC、4.39 V 时 step = **7720 mA**。也就是说即使切到 sp 表、把主板温度压到 25 °C,
高 SOC 段最多也只能到 7720 mA —— **中高 SOC 的瓶颈是电压/SOC,不是温度**。

## 5. 为什么"温度伪装"没用(三组实验)

| 实验 | 结果 | 结论 |
|---|---|---|
| `fixed_temp` 399 | 电池温、热区一起变 | 旧 tpoff 的副作用 |
| `primary_board_temp` 250→400 | `pri=` 跟随,但 chg 表恒 2700 | 温度不是瓶颈 |
| `primary_board_temp` 450 | 掉到 300 | 覆盖链路本身是有效的 |

**结论**:链路没坏,是"这条链路在当前参数集下没有增益"。

## 6. 突破口

### A. 原装闪充头(已实测确认,最有效、零风险)

**2026-11-02 实测:插上原装 120 W 头后**

```
usb_type=8, chg_type=8, bc1p2_type=2, fastchg_is_ok=1, adapter_power=120 (120W)
chg_voltage=9124 (9.1V), charge_protocol=1, vivo_flash_charge_type=1, vchg_state=2
intell_param_type=0[sp]
```

参数集从 `chg` 切到 `sp`,和"vchg_state=0 ⇒ chg"的推断完全对上。此时:

| 主板温度 | sp 表输出 | CMS 请求 | IC CC | 实测 ibat(92% SOC) |
|---|---|---|---|---|
| 42.4 °C(真实) | **3200** | 3200 | 3200000 | 2.68 A |
| 35.0 °C(覆盖) | 7700 | 7700 | 3500000 | 2.46 A |
| 32.0 °C(覆盖) | 15600 | 15600 | 3500000 | 3.07 A |
| 写 0 恢复(42.2) | 3200 | 3200 | 3200000 | 2.69 A |

**结论:温度伪装在原装头下是真实生效的** —— 42 °C 时表只给 3.2 A,压到 35 °C 就请求 7.7 A。
旧 `tpoff` 之所以"看着不好使",一是它同时在写 `fixed_temp`(副作用),二是很可能在
**第三方头(chg 表,41 °C 以下恒 2700)** 的工况下测的,那张表根本不看温度。

注意:高 SOC 时 `refuse_fchg_vbat_thr_mv=4370`,vbat 超过 4.37 V 就不走 CP(电荷泵),
退回 buck 通路,CC 被 `vivo,primary-cur-max-ma=3500` 钳住;所以 92% SOC 下实际电流
只有 2.5–3.1 A,请求值的变化远大于实测变化。低 SOC + CP 介入时才是收益最大的区间。

### B. `tpoff`(统一版):按安装期结果选择伪装范围

一个二进制同时适配两代机型，安装时分别验证倍率和是否牵连电池原始温度:

```
写 fixed_temp=10，读取 dumpsys battery 的 temperature
  100 → fixed_temp_scale=10；10 → fixed_temp_scale=1
同时检查 main_batt_temp 是否跟随写入后的有效值
  跟随 → board-only；不跟随 → both
```

| 模式 | 写入 | 原因 |
|---|---|---|
| `board-only`(X300) | 只写 `primary_board_temp = btb + offset` | `fixed_temp` 在这台就是电池温度,写它会连带压低电池温度、污染保护判断 |
| `both`(iQOO15) | `fixed_temp = 原始温度 + offset` 且 `primary_board_temp = 同一值` | 两个温度必须同步下移,否则电池/主板温差过大会触发"异常"判定,反而更慢 |

其它统一行为:

- 插电判断用 `usb/online` 或 `wls/online`，任一非 online 状态立即解除温度覆盖;
- `game_bypass_charge_flag >= 1` 时立即解除温度覆盖，恢复后才允许再次伪装;
- `game_bypass_charge_flag >= 1` 暂停;退出/断插时清空 `primary_board_temp` 和 `fixed_temp`;
- offset 范围 [-150, 150],`0` 直接退出;
- **写入值硬限幅 [15.0 °C, 55.0 °C]**:低于 15 °C 一律钳到 150(0.1 °C 单位),
  防止冷机或传感器坏值时写出离谱的低温;同时基准温度超出 [-40, 125] °C 视为读失败,直接还原;
- **写后回读校验**:每次写入都读回比对,不一致重写一次,仍不一致则记 `write verify failed`,
  不盲目相信写入结果。

**X300 原装 120 W 头、56–59% SOC 实测**:

| offset | CMS 看到板温 | sp 表输出 | 实测 ibat | 电池功率 | battery / chg_ic |
|---|---|---|---|---|---|
| 不生效(修复前) | 43.8 °C(真实) | 2800 | 2.47 A | ~10 W | 40.6 / 43.9 °C |
| -80 | 36.1 °C | 6200 | 5.8–6.0 A | ~25 W | 40.0 / 44.1 °C |
| **-95** | **35.5 °C** | **7700** | **7.3–7.5 A** | **~32 W** | **40.5 / 45.1 °C** |

(真实 btb 45.3 °C,SOC 从 56% 涨到 59%,约 45%/小时)

offset 与 CMS 看到的板温(sp fbon 表,以 btb≈board 估):-60 → 约 38.5 °C → 3600;
-80 → 36.5 → 6200;-95 → 35.5 → 7700;-115 → 33.5 → 10000;再往下到 ≤32.9 → 15600
(实际受 step 表约 7720/11720 限制)。
注意 btb 通常比 board 高 1–2 °C,`fake = btb + offset` 的实际板温偏移会比 offset 小 1–2 °C。

安全性:这**不是关掉保护,而是把整条温控曲线平移**。btb 涨到 55 °C 时
`fake = 45.5 °C`,sp 表自动降到 1800 mA;btb 到 60 °C → 50.5 °C,继续降档。
所以要盯的是 `bat_btb_temp` / `chg_ic_temp` 这两个**真实**温度,而不是被覆盖的 `primary_board_temp`。

适用:原装头 + 低/中 SOC(此时 sp 表是主限流);高 SOC 段受 step 表与 CV 限制。

### C. `cms_enable=0`(仅作参考,不推荐)

**同样的 CC 上限可以试 §6D 的 `cmsboost`(保留 CMS 保护,但尚未证实有提速效果),所以不推荐这个开关。**

实测(5 V/2 A 适配器,80% SOC):

| | 正常 | `cms_enable=0` |
|---|---|---|
| IC CC | 2700 mA | **3500 mA** |
| FCC votable | 2700 | 12000 |
| IBUS/IBAT vote | 有 | 无(none) |
| 实测 ibat | 1.52 A | 1.76 A(被适配器 2 A 输入限死) |

`vivo,primary-cur-max-ma = 3500` 就是硬件上限。这个开关会让 CMS 停止所有投票
(热、NTC、vbat、健康度保护全丢),**必须配一个用户态温度看门狗**,超温立即 `echo 1` 恢复。

### D. FCC votable 强制(`cmsboost`,**未验证,仅供参考**)

> **状态:未经证实的猜测。** 我们只验证了"能把 `CONSTANT_CHARGE_CURRENT` 的设定值
> 从 2700 mA 改成 3500 mA 并稳住",**没有任何一次实测证明它带来充电功率或时间的提升**。
> 试过的三种第三方头里:5 V/2 A 输入只有 10 W(改了也没用);60 W PPS 和 OPPO UFCS
> 都被识别成 vivo 闪充、走 sp 表 + 电荷泵,`cmsboost` 压根不接管。
> 所以它现在只能算一个**待验证的实验性开关**,不要当作可用的提速手段。

三种第三方充电器实测对比(同一台 X300,60–66% SOC,均开着 `tpoff -95`):

| 充电器 | 协议 / 参数集 | 输入 | 实测 ibat | 电池功率 | `cmsboost` 是否接管 |
|---|---|---|---|---|---|
| 5 V/2 A 普通头 | chg | 4.9 V | 2.47 A | ~10 W | 会接管,但输入限死 |
| 60 W PPS | PPS/UFCS → sp | 8.97 V | 5.46 A | ~23.6 W | **不接管**(CC 已 3.5 A) |
| OPPO 33 W | UFCS → sp | 9.04 V | 5.60 A | ~24.4 W | **不接管** |
| vivo 原装 120 W | vivo 闪充 → sp | 9.1 V | 7.44 A(覆盖后) | ~32 W | 不接管 |

PPS 与 OPPO 都卡在"9 V 档 3 A"这个物理上限(UFCS 请求 `req_ibus=3000`,
`fchg_curr=6000`),所以两者功率几乎一样;原装头能到 32 W 是因为它允许更大的输入电流。

`/sys/kernel/debug/pmic-votable/FCC/` 暴露 `force_val` / `force_active`。写顺序很重要:
**先写 `force_val`,再写 `force_active=1`**;反过来会先用旧值(0)把 CC 置 0,充电会瞬断。

实测(5 V/2 A 适配器,~86% SOC):

| | 基线 | force_val=3500 + force_active=1 | 释放 |
|---|---|---|---|
| FCC effective | USER_SET_INBAT_VOTER 2700 | **DEBUG_FORCE_CLIENT 3500** | 2700 |
| `CONSTANT_CHARGE_CURRENT` | 2700000 | **3500000** | 2700000 |

- 强制能压住 CMS 每 2 s 的投票(连续 20 s 保持 3500);
- 不经过 CMS 的温度表,所以**必须自己做温度看门狗**;
- 它不"改表",而是直接覆盖充电 IC 的 CC;理论上对 `chg` 参数集有效,
  但**没有实测证据**(见本节开头的状态说明);
- **对原装闪充头要小心**:sp/CP 时电流本来是 7.7–15.6 A,硬压 3.5 A 会限速。
  `cmsboost` 用"当前 CC < 3400 才接管、CC > 3800 立即放手"来避免这一点。

`cmsboost.c` 已实现:

```
cmsboost [ceiling_ma] [on_temp] [off_temp]     # 默认 3500 380 400
```

- 插电、`primary_board_temp` 与 `main_batt_temp` 都低于 `on_temp`、且当前 CC 低于 ceiling 时才接管;
- 任一温度到 `off_temp`、拔线、或别的路径把 CC 抬到 ceiling+300 以上,立即 `force_active=0`;
- `SIGTERM` 退出时恢复;自行挂载 debugfs(部分启动里 debugfs 不在 `/proc/mounts` 中)。

**不要和温度伪装同时用**:`tpoff` 的 both 模式会把 `fixed_temp`/`main_batt_temp` 一起压低,
`cmsboost` 的温度看门狗读到的就是假温度,等于把热保护也一起假掉了。
只用 `cmsboost`(或只用 `tpoff` 的 board-only 模式)时,看门狗才是可信的。

**PPS / UFCS 适配器(实测 60 W PPS 与 OPPO 33 W):`cmsboost` 完全不介入**:

```
PPS:  chg_type=8  charge_protocol=3  vchg_state=2  intell_param_type=0[sp]
      fchg_curr_ma=6000  req_ibus_ma=2800  pps_power_derating_ma=200
OPPO: chg_type=2  UFCS            vchg_state=2  intell_param_type=0[sp]
      fchg_curr_ma=6000  req_ibus_ma=3000  ibus_max_thr_ma=3000
```

两者都被识别成 vivo 闪充、走 sp 表 + 电荷泵,CC 本来就是 3500,接管条件不成立。
强行把 FCC 投到 15600 也没有任何效果(电荷泵不看这个投票)。

天花板来自物理与协议,不是温度:2:1 电荷泵要求输入 ≈ 2×vbat ≈ 9 V,
而这类适配器在 9 V 档只给 3 A → 电池 6 A ≈ 26 W。实测 PPS 5.46 A / 23.6 W、
OPPO 5.60 A / 24.4 W,都已是天花板的 ~90%。温度侧 `tpoff` 也早把 sp 表拉满(15600),
没有更多空间;想更快只能换 9 V 档能吃更大电流的适配器,或 vivo 自家闪充头。

### 决策树

```
充电器被识别成 vivo 闪充吗?(原装头 / PPS / UFCS → 是)
├─ 是 → 走 sp 表 + 电荷泵:tpoff 压板温(原装头实测 10W → 32W)
│        9V 档第三方头(PPS/UFCS)约 24W,受适配器 3A 限制,温度侧已拉满
└─ 否 → 普通 DCP/PD 头,落 chg 表,上限 2700
         ├─ 想要可逆、保留 CMS 保护 → cmsboost(FCC 强制 3500,**未验证是否提速**)
         └─ 更激进、放弃所有保护 → cms_enable=0(CC 3500,无热保护)
```

## 7. 已放弃 / 不推荐的路线

| 路线 | 结论 | 原因 |
|---|---|---|
| 内核模块改表(`gen_module.py` 嫁接原厂 .ko) | **放弃** | 两次 `insmod` 都在**加载阶段 panic**(自己的 printk 一条都没出来),重启后 KernelSU 失效、需要重刷 boot。已排除签名(原厂模块尾部同样没有 `~Module signature appended~`)和 vermagic;剩下最可能是模板构建 `g34069a564b04` 与运行内核 `g0a092cc0037a` 的 `struct module` 布局 / kCFI 类型哈希不一致。**除非拿到与运行内核完全匹配的 .ko 作模板,否则不要再走这条路。** |
| `cms_enable=0` | 不推荐 | 能把 CC 抬到 3.5 A,但 CMS 的热、NTC、vbat、健康度保护会一起失效;同样的上限可以试 `cmsboost`(未验证),至少保留温度看门狗。 |
| 旧版 `tpoff`(无条件同时写 `fixed_temp`) | 已合并 | 新版 `tpoff` 在安装期分别检测 `fixed_temp` 倍率和 `main_batt_temp` 是否被牵连，自动选择只写板温或同时写入；不需要再维护两个工具。 |

### 7.1 备查:表在内存里的位置(kprobe 实测,零风险)

万一以后拿到匹配内核的模块可以复用,这里保留已经验证过的布局:

- wired fbon 组基址 `ctx+0xb720`,wired fboff `ctx+0xb840`,无线 fbon `ctx+0xb968`,无线 fboff `ctx+0xba88`;
- 每组 6 个 kind,间隔 `0x30`:`+0x00 hdr_pri`,`+0x30 data_pri`,`+0x60 hdr_par`,
  `+0x90 data_par`,`+0xc0 hdr_bat`,`+0xf0 data_bat`;kind 内按 `type*8` 索引
  (type 0=sp 1=eq 2=bypass 3=chg 4=qc 5=ai-rate);
- 表头 `{rows, 3}`,数据 `rows × {low, high, ma}`。

| 组 | chg(type3) 数据地址 | 末行 mA |
|---|---|---|
| wired fbon | `ctx+0xb768` | 2700 |
| wired fboff | `ctx+0xb888` | 2700 |
| 无线 fbon / fboff | `ctx+0xb9b0` / `ctx+0xbad0` | 2000 |

查表可以用 `kprobe_events` 的 fetchargs 直接读,读失败不会 oops:

```sh
T=/sys/kernel/tracing
echo 'p:tcptr vfcs_cms_get_intell_chg_current chip=%x0 d=+0xb768(%x0):u64' > $T/kprobe_events
echo 1 > $T/events/kprobes/enable; echo 1 > $T/tracing_on
sleep 3; grep tcptr $T/trace
echo > $T/kprobe_events; echo 0 > $T/events/kprobes/enable
```

拿到指针后可以用 `@绝对地址:u32` 逐个读表项。

## 8. 复现与回滚

```bash
# 温度链路验证(只读)
adb shell su -c 'cat /sys/class/cms_class/primary_board_temp /sys/class/cms_class/fixed_temp'
adb shell su -c 'dmesg | grep -E "get_intell_chg_current|select_intell_param_type"'

# 主板温度独立覆盖
adb shell su -c 'echo 250 > /sys/class/cms_class/primary_board_temp'
adb shell su -c 'echo 0   > /sys/class/cms_class/primary_board_temp'   # 解除

# tpoff(统一版;模块安装时已完成机型和 fixed_temp 单位判定)
adb push tpoff /data/local/tmp/ && adb shell su -c 'chmod 755 /data/local/tmp/tpoff'
adb shell su -c 'nohup /data/local/tmp/tpoff -95 board 10 >/dev/null 2>&1 &'   # -95: X300 上 sp 表 7700mA
adb shell su -c 'killall tpoff'    # 停止；下次启动会先清除覆盖

# cmsboost(FCC 强制 + 温度看门狗;默认 3500mA / 38°C 开 / 40°C 关)
adb push cmsboost /data/local/tmp/ && adb shell su -c 'chmod 755 /data/local/tmp/cmsboost'
adb shell su -c 'nohup /data/local/tmp/cmsboost >/dev/null 2>&1 &'
adb shell su -c 'cat /data/local/tmp/cmsboost.log'
adb shell su -c 'killall cmsboost'    # 退出即 force_active=0

# 手动强制(先 val 后 active!顺序反了会把 CC 置 0)
adb shell su -c 'echo 3500 > /sys/kernel/debug/pmic-votable/FCC/force_val'
adb shell su -c 'echo 1    > /sys/kernel/debug/pmic-votable/FCC/force_active'
adb shell su -c 'echo 0    > /sys/kernel/debug/pmic-votable/FCC/force_active'   # 恢复

# cms_enable(高风险)
adb shell su -c 'echo 0 > /sys/class/cms_class/cms_enable'
adb shell su -c 'echo 1 > /sys/class/cms_class/cms_enable'   # 恢复
```

**回滚**:所有改动都是内存态;`primary_board_temp`/`fixed_temp` 写 0、`cms_enable` 写 1、
`FCC/force_active` 写 0、重启均可还原。内核模块重启即消失。

### 9.5 关键节点

| 节点 | 语义 |
|---|---|
| `primary_board_temp` | 主板温度;写入=覆盖,写 0=取消 |
| `fixed_temp` | **电池温度**替代值(会影响 battery/temp 与热区) |
| `bat_btb_temp` | 电池 BTB NTC,真实值,不被上面两个影响 |
| `main_batt_temp` | 电池温度(会被 fixed_temp 覆盖) |
| `chg_ic_temp` / `charge_sub_temp` | 充电 IC 温度 |
| `cms_enable` | CMS 总开关;0 = 停止投票并重置 votable |
| `switch_state` | sp/eq 选择(实测对 chg 参数集无效) |
| `debug_chg_cur` | 独立 Min 投票,只能降不能升 |
| `pmic-votable/FCC/force_{val,active}` | 直接覆盖充电 IC 的 CC(先 val 后 active) |
| `pmic-votable/USER_IBUS/force_{val,active}` | 输入限流的强制入口(未验证,慎用) |

> 注:部分测量时 ExtremeGT 模块的 `tpoff` 仍在后台(`fixed_temp`/`primary_board_temp` 被 -6 °C 偏移),
> 所以上表里的"真实板温"是相对 tpoff 偏移后的值;表查表的相对关系不受影响。
