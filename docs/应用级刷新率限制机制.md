# vivo 应用级刷新率限制机制分析（红果短视频 90Hz 案例）

> 设备：vivo V2505A（PD2505，Android 17 / SDK 37，KernelSU root）
> 分析日期：2026-11-06
> 现象：使用红果短视频（com.phoenix.read）时刷新率被限制在 90Hz，其它大部分应用为 120Hz。

## 结论（TL;DR）

红果的 90Hz **不是全局刷新率设置、也不是 App 自己请求的**，而是 vivo「应用自定义刷新率」功能的**内置默认档位**：

- vivo 在 GameWatch 的加密配置里给每个应用预置了默认刷新率（120/90/60 三档名单），`com.phoenix.read` 位于 **90Hz 档**。
- GameWatch 将每应用 fps 通过 binder 推给 system_server 内的 **vivo_rms（RRM）**，RRM 的 `WindowRequestManager` 按**前台窗口**应用帧率上限。
- 因此修改全局 `vivo_screen_refresh_rate_mode`（Scene 接管刷新率）**无法解除**应用级 90Hz 上限。
- 解决：设置 → 显示与亮度 → 屏幕刷新率 → 应用刷新率，把红果改为 120Hz。

## 证据链

### 1. App 侧无帧率请求

红果 base.apk 全部 23 个 dex 扫描结果：

- `setFrameRate`（Surface API）：仅 1 处命中且为 `MediaFormat.setFrameRate`（`com.lynx.animax.player.VideoAssetExtractor`，读视频元数据），非 Surface；
- `setFrameRateCategory` / `FrameRateCategory`：0 命中；
- `preferredRefreshRate` / `preferredDisplayModeId`：0 实际调用；
- vivo RMS SDK（`acquireRefreshRate` / `com.vivo.rms`）：0 命中。

即红果没有通过任何 API 主动请求 90Hz。

另外 `dumpsys display` 中 `frameRateCategoryRate {normal=60.0, high=90.0}` 来自 SurfaceFlinger native（`SurfaceControl.DynamicDisplayInfo`，`LocalDisplayAdapter$LocalDisplayDevice.updateFrameRateCategoryRatesLocked` 读取），是给显式请求帧率类别的 App 用的映射，与本案例无关。

### 2. 默认值来源：GameWatch 加密配置

组件：`/system/app/GameWatch/GameWatch.apk`（包名 `com.vivo.gamewatch`）。

- 资产 `assets/vge_configs_6154.zip` 内 `display_refresh_rate_adjuster.xml`（1.18MB，**AES 加密**，运行时解密），按三档维护包名名单：
  - HIGH → 默认 120Hz（`f2109m`）
  - MID  → 默认 90Hz（`f2121y`），**com.phoenix.read 在此档**
  - LOW  → 默认 60Hz（`f2115s`）
- 解密后的默认判定：`e0.c0.z0(String pkg)`

```java
// e0/c0.java
public int z0(String str) {
    if (f2109m.contains(str) || F(str)) return mSupportedRefreshRates.contains(120) ? 120 : 90; // HIGH
    if (f2121y.contains(str))           return mSupportedRefreshRates.contains(90)  ? 90  : 120; // MID
    return 60;                                                                                     // LOW
}
```

### 3. 用户修改的存储与暴露

- GameWatch SharedPreferences：`user_manual_fps_set_prefs`，键 `key_prefs_set_pkg_state_ultra/high/mid/low`（`c0.O0()` 写入）。
- ContentProvider：`content://com.vivo.gamewatch.fpsprovider/manual_fps_set`
  （`com.vivo.gamewatch.modules.display.UserManualFpsProvider`），向 Settings 暴露 `packagename / state / defaultrate / supportrates` 列。
- Settings 侧对应代码：
  - `com.vivo.settings.display.VivoCustomAppRefreshRateAppsCategoryController`（列表/条目 UI）
  - `com.vivo.settings.display.f7`（ScreenRefreshAppManager，cursor 查询 fpsprovider）
  - 入口 Fragment：`ScreenApplicationRefreshFragment`，总开关 `Settings.Secure` 键 **`vivo_promotion_switch_setting`**（"1"=开）。

### 4. 下发与执行链路

```
GameWatch e0.c0.E0(per-app fps map)
  └─ SystemBridgeManager.setBundle("key_app_fps_settings" |
                                    "key_disable_promotion_settings" |
                                    "key_promotion_settings", bundle)
       └─ binder → vivo_rms (RrmServer, system_server)
            └─ com.vivo.services.rrm.WindowRequestManager
                 (同时是云控配置 fps_xml_settings / disable_promotion_settings 的消费者)
                 └─ setFpsSettings() / setDisablePromotionSettings()
                      → FpsXmlSettings.packageFpsXmlSettings[pkg] = fps
                 └─ getWindowFpsParam() / applyWindowRefreshRate()
                      → 前台窗口按包名匹配 → 渲染帧率上限 = 该应用的配置值
```

关键代码位置（vivo-services.jar）：

- `WindowRequestManager.onLineConfigChange()` — 接收 `key_app_fps_settings` / `key_disable_promotion_settings`
- `WindowRequestManager.getWindowFpsParam()` — `FRAME_RATE_TYPE_*` 三分支（LayoutParam / FrameOverride / NonHighRefreshRate），fps 最终 `min(fps, getUserSettingMaxRefreshRate())`
- 相关在线配置缓存文件（QoS）：`/data/bbkcore/sceneconfig.0.xml`（`ConfigConstants.QOS_CONFIG_FILE`）

### 5. 全局 key 的写入者排查

`vivo_screen_refresh_rate_mode`（1=智能, 60/90/120=固定档）经 RRM `GlobalConfigs$UserSettingObserver` 读取并转换为 DisplayModeDirector 投票（`PRIORITY_USER_SETTING_*`，实测投票 min/max 与 key 值同步翻转 60↔120）。

对已反编译的全部系统组件交叉验证（framework.jar / services.jar / vivo-framework.jar / vivo-services.jar / PowerEffectManager / AppBehaviorEngine / SuperProcessSystem / Libra / GameWatch / Settings 等）：

- **唯一写入者**：`com.vivo.settings.display.ScreenRefreshModeToggleController`（Settings.apk，第 105 行 `Settings.Global.putInt(KEY_VIVO_SCREEN_REFRESH_RATE_MODE, ...)`）；
- 其余组件（WMS SettingsObserver、RRM GlobalConfigs、PEM SceneDynamicParamPlugin、ABE t2.a、SuperProcessSystem g/s、Libra 热策略、GameWatch 统计等）**均为读取方**。

注：分析期间观察到 key 在 60↔120 间动态翻转，但静态代码中找不到对应的自动写入方；如确认存在自动覆盖，需运行期抓（见下）。

## 对 Scene 接管刷新率的影响

- 两层独立：`vivo_screen_refresh_rate_mode` 决定**全局档位/上限**；GameWatch→RRM 的每应用配置在该上限之下**再按包名限流**。Scene 只改全局 key，红果依然 90Hz。
- Scene 写入被覆盖的问题：全局 key 除 Settings 切换控件外未找到其它 Java 写入者；若确有后台自动改写，需要动态捕获确认来源。

## 解决方案

1. **推荐（用户态）**：设置 → 显示与亮度 → 屏幕刷新率 → 应用刷新率 → 红果免费短剧 → 选 120Hz。
   路径：Settings UI → fpsprovider update → GameWatch prefs → `c0.K0()/y0()` → `E0()` → `SystemBridgeManager.setBundle("key_app_fps_settings")` → RRM 即时生效，OTA 升级保留。
2. **改默认值**：需替换 GameWatch 的 `display_refresh_rate_adjuster.xml`（AES 加密），或 hook `e0.c0.z0(String)` 对目标包名返回期望档位。
3. **hook 点（研究用）**：
   - GameWatch：`e0.c0.z0()`（默认值）、`e0.c0.E0()`（下发内容）
   - RRM：`WindowRequestManager.setFpsSettings()` / `getWindowFpsParam()`（system_server）
4. **动态抓 key 写入者**：frida 注入 system_server 被 SELinux `execmem` 拒绝（dmesg 有 `avc: denied { execmem } for comm="system_server"`，vivo 已加固）；改用 **LSPosed** hook `Settings.Global.putString/putStringForUser/putInt`（Zygote 集成不走 ptrace，可绕过该限制）。

## 分析过程中的环境记录

- 设备在 frida 反复注入失败期间重启过一次；分析结束时 `su` 需重新授权（KernelSU）。
- `persist.sys.log.ctrl` 曾被临时设为 `yes` 以尝试开启 vivo 日志（VLog 未实际输出），可按需还原为 `no`。
- 分析结束时 `vivo_screen_refresh_rate_mode` 当前值为 120（会话起始为 60）。
- 中间产物：jadx 1.5.3 反编译源码、`RrpConfig.json`、phoenix.apk dex 扫描结果等位于本机 `C:\Users\hello\AppData\Local\Temp\vivo_rms\`（临时目录，重启后丢失）。
